[2.12.4](https://github.com/gina-io/swig/tree/v2.12.4) / 2026-11-18
-------------------------------------------------------------------

* **Fixed** In native swig, swig-twig and swig-jinja2 a variable named with a JavaScript reserved word, such as `{{ class }}`, `{{ super }}`, `{{ enum }}`, `{{ const }}` or `{{ import }}`, renders its value from the context on both render paths, where it failed to compile with a raw JavaScript SyntaxError; swig-django already rendered it. A macro named `__k` called inside a for loop renders in native swig and swig-jinja2 instead of throwing. A loop variable or a macro parameter named like a name the compiled code uses no longer hides that name: in native swig and swig-twig, a loop variable named `_output` no longer drops the loop's output: `{% for _output in xs %}[{{ _output }}]{% endfor %}` over `["A", "B"]` renders `[A][B]` on both render paths, where it rendered an empty string, as does a two-name loop with `_output` as its key or its value; in swig-twig, `{% for _utils in [1] %}` around a range renders `[12]` where it threw « _utils.isArray is not a function », `{% for _ext in [1] %}` around `2 is even` renders `[Y]` where the test read false, and macro parameters named `_utils` or `_ext` behave the same way; in swig-jinja2, a macro parameter named `_ext` no longer makes `2 is even` false, and one named `Math` no longer makes `2 ** 3` render an empty string.

* **Fixed** A name an object gets only from Object.prototype reads as missing, bare or dotted, in all four flavors and on both render paths: `{{ toString }}`, `{{ valueOf }}`, `{{ hasOwnProperty }}`, `{{ isPrototypeOf }}`, `{{ toLocaleString }}`, `{{ __lookupGetter__ }}` and `{{ obj.toString }}` render an empty string, where native swig, swig-twig and swig-jinja2 printed the function's source and swig-django called it (`[object Object]`, `false`, or an empty string for `__lookupGetter__`), and `{% if toString %}` no longer takes its branch, also after a loop over that name: `[{{ toString }}]{% for toString in xs %}{% endfor %}[{{ toString }}]` renders `[][]`, and `{% if valueOf %}` after a loop over `valueOf` is not taken. In native swig, swig-twig and swig-jinja2 a macro parameter of such a name reads its argument: `{% macro m(toString) %}[{{ toString }}]{% endmacro %}{{ m("X") }}` renders `[X]`, where it printed the function's source, and `{{ toString() }}` in that macro calls the argument, where it rendered `[object Undefined]`. swig-django also reads as missing a function added to Object.prototype and a function a Proxy returns for such a name, instead of calling it. A key of that name the object holds itself, and a method of the object's own class, read as before.

* **Fixed** A context key that holds null or undefined and is named like a standard JavaScript global or a name the compiled code uses no longer lets that global or name through, in native swig, swig-twig and swig-jinja2: with such a key, `{{ _output }}` rendered the output so far (`[[]`), `{{ Math }}`, `{{ JSON }}`, `{{ _utils }}` and `{{ _ctx }}` rendered `[object Object]`, `{{ Date }}` and `{{ Object }}` rendered the function's source, and `{{ __l }}` inside a loop rendered the list looped over; each renders an empty string now, as in swig-django. `Math is none` (swig-jinja2), `Math is null` (swig-twig) and `Math is None` (swig-django) are true for such a key, where they were false. With no such key in the context, a global a template reads (`Math`, `JSON`, `Date`, `encodeURIComponent`) is read as before, also after a loop variable named `Math` or `JSON`. When the context has no key of the name at all, `{{ _output }}` rendered the output so far, `{{ _utils }}`, `{{ _swig }}`, `{{ _filters }}` and `{{ _ext }}` rendered `[object Object]`, `{{ _fn }}` rendered the source of a function, and `{{ __l }}` and `{{ __len }}` inside a loop rendered the list looped over and its length; each renders an empty string now too, while `{{ _ctx }}`, and `{{ _exports }}` on the async render path, still render `[object Object]`. A key that holds null and is named like another global, such as `setTimeout`, still lets that global through.

* **Fixed** Behaviour that changes with these fixes: in native swig, swig-twig and swig-jinja2 an include inside a macro, and a macro called inside it, see a macro parameter named like a standard JavaScript global, a name the compiled code uses, a member objects get from Object.prototype, one of the nine words that only strict-mode JavaScript reserves (`yield`, `let`, `static`, `implements`, `interface`, `package`, `private`, `protected` and `public`) or `await`, on the sync render path, such as `document`, `_ext`, `_parentTpl`, `toString` or `public` (`{% macro m(document) %}[{% include "p.html" %}]{% endmacro %}{{ m("X") }}`, with p.html holding `{{ document }}`, renders `[X]` on the sync path, where it rendered `[]` (and `[object Object]` with a parameter named `_ext`, and the function's source with one named `toString`), and `{% macro inner() %}{{ document }}{% endmacro %}{% macro m(document) %}[{{ inner() }}]{% endmacro %}{{ m("X") }}` renders `[X]` on both render paths, where it rendered `[]`), while they still see no other parameter; in swig-jinja2 a default that reads a parameter of such a name, an earlier one, its own or a later one, reads that parameter (its argument or, when the call gives none, the value its own default gave it once that default has run, and an empty value otherwise) also when the context holds a key of the same name, as Jinja2 does: with a context key `process` holding `"CTX"`, `{% macro m(process, b=process) %}[{{ b }}]{% endmacro %}` renders `[X]` for `{{ m("X") }}` and `[]` for `{{ m() }}` on both render paths, where it rendered `[CTX]` for both, `{% macro m(process=process) %}[{{ process }}]{% endmacro %}{{ m() }}` renders `[]` and `{% macro m(a=process, process="D") %}[{{ a }}|{{ process }}]{% endmacro %}{{ m() }}` renders `[|D]`, where they rendered `[CTX]` and `[CTX|D]`, while with `zz` for `process` these templates still render the context's key (`[CTX]`, `[CTX]`, `[CTX]` and `[CTX|D]`), where Jinja2 renders `[X]`, `[]`, `[]` and `[|D]`; in swig-jinja2 a macro called from such a default reads a parameter of such a name of the calling macro, its own or a later one, as empty, also when the context holds a key of that name: with the context key `process` holding `"CTX"`, `{% macro h() %}{{ process }}{% endmacro %}{% macro m(b=h(), process="D") %}[{{ b }}|{{ process }}]{% endmacro %}{{ m() }}` renders `[|D]` on both render paths, where it rendered `[CTX|D]`, which Jinja2 renders; in native swig, swig-twig and swig-jinja2 a macro defined inside another macro and called after that macro has returned no longer sees a parameter of such a name of the macro that defined it, which it sees when called inside that macro, and reads the name as the rest of the template does: `{% macro outer(_ext) %}{% macro inner() %}[{{ _ext }}]{% endmacro %}{% endmacro %}{{ outer("X") }}{{ inner() }}` renders `[]` on both render paths, where it rendered `[X]`, while with `zz` for `_ext` it still renders `[X]` (Jinja2 raises an error for that call, as `inner` is local to `outer`); in native swig, swig-twig and swig-jinja2 a `{% set %}` of a parameter of such a name inside its macro no longer stays in the context after the call when the context holds no key of that name: `{% macro m(document) %}{% set document = "S" %}{% endmacro %}{{ m("A") }}[{{ document }}]` renders `[]` on both render paths, as Jinja2 does, where it rendered `[S]`, while with `zz` for `document` it still renders `[S]`, where Jinja2 renders `[]`; in native swig and swig-twig a macro defined inside a for loop and called after the loop reads a loop variable of such a name (also the key or the value of a two-name loop) as the rest of the template does, where it read the variable's last value when the context held no key of that name, or one holding null or undefined (for `arguments` it printed `[object Object]`, and for `toString` with no such key the function's source): `{% for document in xs %}{% macro m() %}[{{ document }}]{% endmacro %}{% endfor %}{{ m() }}` over `["A", "B"]` renders `[]` on both render paths, where it rendered `[B]`, while with `zz` for `document` it still renders `[B]` (Jinja2 raises an error for that call, as `m` is local to the loop); swig-jinja2 no longer reads a global for a loop item that is null or undefined (`{% for Math in xs %}[{{ Math }}]{% endfor %}` over `[undefined, null, 1]` renders `[][][1]`, as the other flavors do, where it rendered `[object Object]` for the first two); in all four flavors `{{ __k }}` inside a one-name loop reads the context, an empty string or the context's `__k`, where it rendered the loop's index; and in native swig, swig-twig and swig-jinja2 a dotted read whose first name is a context key without that member no longer falls back to the global of that name: with `Math` holding `{}`, `{{ Math.PI }}` renders an empty string where it rendered 3.141592653589793, and in swig-jinja2 `Math.PI == x` is false there, as in Jinja2 (`{{ Math.PI }}|{% if Math.PI == x %}Y{% else %}N{% endif %}` with `x` 3.141592653589793 renders `|N` where it rendered `3.141592653589793|Y`). A call reads its name as a plain variable read now does, in native swig, swig-twig and swig-jinja2 and on both render paths: with no context key of the name, `{{ toString() }}` renders an empty string where it rendered `[object Undefined]`, `{{ valueOf() }}` and `{{ hasOwnProperty("a") }}` render an empty string where they threw « Cannot convert undefined or null to object », and `{{ class() }}`, `{{ _output() }}` and `{{ _utils() }}` render an empty string where they failed to compile or threw, while a function under a `class` key is called where the template failed to compile, and one under a `toString` key is called as before; a context key that holds undefined counts as a key: with one named `encodeURIComponent`, `{{ encodeURIComponent("a b") }}` renders an empty string where it rendered `a%20b`, and in swig-jinja2, with one named `Math`, `Math == none` and `Math in [none]` are true and `Math != none` is false, the reverse of before; and a native tag registered with setTag gets the same reads in the compiled fragments it receives: a tag that outputs its argument renders an empty string for `toString` when the context has no such key, where it printed the function's source, and renders the value of a `class` key, where the template failed to compile; for `f (1)`, a call written with a space before its parenthesis, such a tag receives a call that runs, where the template failed to compile with a SyntaxError. A method that a value gets only from Object.prototype reads as missing when the template calls it, in native swig, swig-twig and swig-jinja2 and on both render paths, as a call after a subscript (`{{ os[0].hasOwnProperty("a") }}`) already read it in 2.12.2 and 2.12.3: `{{ o.hasOwnProperty("a") }}` renders an empty string where it rendered `true`, `{% if o.hasOwnProperty("a") %}` no longer takes its branch, and `{{ o.toString() }}` with `o` a plain object, `{{ a.valueOf() }}` with `a` holding `[1, 2]` and `{{ s.toLocaleString() }}` with `s` holding `"1234.5"` render an empty string where they rendered `[object Object]`, `1,2` and `1234.5`, while the methods that numbers, strings and dates define themselves, such as a number's `toString` or a Date's `valueOf`, and a method of the object's own class are called as before; to test for a key, write `"a" in o` in native swig and `o.a is defined` in swig-twig and swig-jinja2 (false there for a key that holds null), and to print the value, write `{{ o }}`.

* **Fixed** swig-jinja2 `{{ super() }}` and swig-twig `{{ parent() }}` fail at compile, wherever the call stands and on both render paths, with « "super()" is not supported (swig-jinja2 does not render parent blocks) » or « "parent()" is not supported (swig-twig does not render parent blocks) » and the line and file: neither flavor renders a parent block's content. Before, swig-jinja2 failed with a raw « 'super' keyword unexpected here » SyntaxError where the template was compiled, and ignored the call at the top level of an extending template outside its blocks, and on the sync path in a block the parent does not define and at the top level of an imported file; swig-twig rendered the overriding block without the parent's content, and called a macro, an imported macro or a function from the data named parent. A read of the name (`{{ parent }}`, `{{ parent.x }}`) and a call of a member of that name (`{{ o.parent() }}`) are unchanged.

* **Fixed** On the async render path a macro whose compiled code holds the word `await` no longer throws « The macro … holds an {% include %}, {% import %}, {% from %} or {% block %}, which the async render path does not support inside a macro. » when it holds none of them, in native swig, swig-twig and swig-jinja2: the word in the macro's text, in a string it writes, in a for loop, with, filter, apply or set block inside it, or as the name of a parameter, of a variable it reads, of a loop variable or of a `{% set %}` no longer counts, so in native swig `{% macro m() %}<i>await</i>{% endmacro %}[{{ m() }}]` renders `[<i>await</i>]` on both render paths, and in the three flavors `{% macro m(await) %}[{{ await }}]{% endmacro %}{{ m("X") }}` renders `[X]`, where they threw on the async path; a macro that holds a real include, import, from import or block, or a native tag registered with setTag whose compiled code awaits, still throws. A template compiled with `codegenMode: 'async'` by 2.12.3 keeps the error until it is compiled again. A tag registered with setTag whose compiled code writes `await` on a line after a quote that is not part of a single- or double-quoted string literal (in a regular expression, a comment or a template literal), with another quote of the same kind later on that line, is no longer seen as awaiting: on the async render path a for loop or its else or empty branch, a with, filter, apply or set block, a swig-django spaceless block or a macro (also one that is never called) holding such a tag then fails to compile with a SyntaxError, where 2.12.3 rendered the loop or the block and a template that only defines the macro, and threw the macro error when the macro was called.

* **Fixed** Templates compiled by 2.12.3 or earlier keep their old reads for these fixes until they are recompiled with 2.12.4: in native swig, swig-twig and swig-jinja2 the compiler decides each read these entries change, and in swig-django it decides `{{ __k }}` in a one-name loop and `Math is None` on a key that holds null. swig-django's reading of a function an object gets from Object.prototype as missing (`{{ toString }}`, `{{ o.toString }}`, `{% if toString %}`) is decided by its runtime and reaches such templates at once, except after a loop over that name, where such a template puts the function back as a key of the context (`[{{ toString }}]{% for toString in xs %}{% endfor %}[{{ toString }}]` renders `[][[object Object]]` until it is recompiled). A template compiled by 2.12.4 keeps its new reads on the 2.12.3 runtime, except in swig-django, whose 2.12.3 runtime still calls those functions. Recompile precompiled templates (swig compile output, registerBundle bundles, stored precompile() results) with 2.12.4.
