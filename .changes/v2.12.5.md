[2.12.5](https://github.com/gina-io/swig/tree/v2.12.5) / 2026-11-18
-------------------------------------------------------------------

* **Fixed** A for loop, in all four flavors, and a swig-django `{% cycle %}` tag no longer fail to compile when `Math.random()` returns a value under 1e-6 (about one draw in a million; each loop or cycle tag draws once when its template compiles): the compiled code names the loop's scratch variable and the cycle's state key from that value, and such a value prints in exponent form (`1.5e-7`), whose minus sign made the template fail with « Unexpected token '-' » or « Invalid left-hand side in assignment » on both render paths. Every other value gives the same name as before, so compiled code is otherwise unchanged.

* **Fixed** A template function compiled with `codegenMode: 'async'` and registered with `register()`, `registerBundle()` or `run(tpl, locals, path)` is now used on the async render path, in all four flavors: `renderFile(path, locals, cb)` with an async loader, `compileFile(path, { codegenMode: 'async' })`, and the `{% include %}`, `{% import %}`, `{% from %}` and `{% extends %}` of templates rendered on that path (import and from in the flavors that have them) read it before the loader, where they failed with the loader's not-found error, or used the loader's source when the loader also held the name. It then takes part in the render that reaches it, as a template from the loader does: a `{% set %}` in a registered include reaches the including template, and a registered template that includes or extends itself stops with the nesting or the circular-extends error. A sync-compiled registration, such as the swig CLI's output, is still used by the sync calls only. A function compiled in async mode by 2.12.4 is used as it is.

* **Fixed** swig-django: a `{% cycle %}` tag keeps its position for one render of its template, as Django keeps it, on both render paths. An included template's cycle starts again at each include, where under the default memory cache it could carry on from an earlier include of the same template: a for loop over three items that includes a template holding `{% cycle "i1" "i2" "i3" %}` rendered `i1i2i3` and now renders `i1i1i1`, which Django renders (with `cache: false` it already rendered `i1i1i1`). A cycle inside a `{% with %}` body carries on across the iterations of an enclosing loop: `{% for x in xs %}{% with a=1 %}{% cycle "a" "b" %}{% endwith %}{% endfor %}` over three items renders `aba`, which Django renders, where it rendered `aaa` with and without the cache. The change is in the compiled code: a template compiled by 2.12.4 keeps its old cycle positions until it is recompiled, and one compiled by this release renders the new positions on the 2.12.4 runtime too.
