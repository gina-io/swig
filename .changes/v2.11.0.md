[2.11.0](https://github.com/gina-io/swig/tree/v2.11.0) / 2026-11-02
-------------------------------------------------------------------

* **Added** swig-jinja2: Jinja2's comparison tests `eq`, `equalto`, `ne`, `lt`, `lessthan`, `le`, `gt`, `greaterthan` and `ge`, which 2.10.0 treated as unknown tests. Each test gives what the operator it names gives, bare, after `is not` and with a parenthesized argument: `x is eq 1` is `x == 1` and `count is lt 10` is `count < 10`, so `eq` and `ne` compare with Python's equality, as `==` and `!=` do, and `"1" is eq 1` is false. An ordering test compares lists by their text, as `<` does (`[2] is lt [10]` is false), and where Jinja2 raises because it cannot order the two values (a string and a number, a list and a number, None or a missing value), it gives what its operator gives. Each test takes one argument: with none or with two it fails when it is reached, as in Jinja2, and a signed number after the name is not its argument (`x is gt -1` reads as `(x is gt) - 1`), so write `x is gt(-1)`. A test registered under one of these names with `setExtension('_test_<name>', fn)` before the template compiles runs in place of the operator, with any number of arguments. `"eq" is test` and `"==" is test` are true, as in Jinja2; the `escaped` test is not provided, and `x is in y` does not parse (write `x in y`).

* **Fixed** swig-jinja2 and swig-django: `==` and `!=` compare as Python does, where until 2.10.0 they were JavaScript's loose operators. A string never equals a number or a boolean: `page == 1` is false when `page` is the string "1", and so are `"" == 0`, `"1" == True` and `[1] == 1`. Lists and mappings compare item by item: `[1] == [1]`, `[True] == [1]` and `{"a": 1, "b": 2} == {"b": 2, "a": 1}` are true, where two equal lists were two objects and so unequal; a date equals a date of the same time. In swig-jinja2 a variable or attribute that is missing or holds None reads as None instead of an empty string: `x == ""`, `x == 0` and `x == false` are false for it, and `x == none` stays true for it, as `x is none` reads it (Jinja2 tells a missing value from None, so there `x == none` is false for a missing `x`); the elements of a list or mapping literal read their own value too, so `[x] == [none]` and `{"k": x} == {"k": none}` are true when `x` holds None. The comparison is in the compiled code: recompile precompiled templates to pick it up.

* **Fixed** swig-jinja2 and swig-django: `in` compares the items of a list with Python's equality, as Jinja2 and Django do: `True in [1]`, `1 in [True]` and `0 in [False]` are true, lists and mappings compare item by item (`[1, 2] in [[1, 2]]`, `[] in [[]]`, `{"k": 1} in [{"k": True}]`), and a date equals a date of the same time; until 2.10.0 an item matched only the identical value. In swig-jinja2 the operands, and the elements of a list or mapping literal, also read their own value, where until 2.10.0 a variable or attribute that was missing or held None read as an empty string; a missing value equals None, as `x is none` reads it (Jinja2 tells the two apart). So `x in [none]` is now true when `x` is missing or holds None, `x in [""]` and `"" in [x]` are false for it, and a missing or None value tested against a string (`x in "abc"`), or a string tested against a missing or None container (`"" in x`), is false. `not in` is the negated test. The operand reads are in the compiled code: recompile precompiled templates to pick them up.

* **Fixed** swig-jinja2: `divisibleby` and `sameas` with no argument or with two fail when the expression is reached, as in Jinja2, instead of giving a value. A signed number after the name is not the argument, so `x is divisibleby -3` reads as `(x is divisibleby) - 3`, a test with no argument, and in 2.10.0 `{% if x is divisibleby -3 %}` and `{% if x is sameas -1 %}` took their branch whatever x was; write `x is divisibleby(-3)`. A test registered under one of these names with `setExtension('_test_<name>', fn)` still receives any number of arguments.
